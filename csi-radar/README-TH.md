# CSI Motion Observatory — ต่อจากโปรเจกต์เดิม

วันที่จัดทำ: 14 พฤศจิกายน 2026

## ผลงานที่มีให้ในชุดนี้

- Python backend รับเฟรม `CSI,timestamp_us,rssi,count,amp...` ตรงกับเฟิร์มแวร์เดิม ไม่อ่าน Serial บนเธรดหน้าจอ
- หน้าเว็บภาษาไทย แสดง RSSI, motion energy, จำนวนเฟรมต่อวินาที, amplitude และเหตุการณ์
- คาลิเบรต 10 วินาที, ใช้ threshold และ hysteresis ลดการสลับสถานะ
- ข้อมูลหายเกิน 2 วินาทีแสดง DISCONNECTED ไม่ค้างผลตรวจจับว่าเป็นข้อมูลล่าสุด
- ส่งออก CSV สูงสุด 18,000 เฟรมล่าสุดในหน่วยความจำ ต้องดาวน์โหลดก่อนปิดโปรแกรม
- โหมดจำลองแยกชัดเจน ไม่มีการสลับข้อมูลจำลองมาแทนเซนเซอร์อัตโนมัติ
- รับข้อมูลผ่าน UDP สำหรับเฟิร์มแวร์ใหม่ และ Serial สำหรับเฟิร์มแวร์เดิม
- ตัวเชื่อมโมเดลเดิมเป็นตัวเลือก คง feature extraction เดิมและใช้ `model.classes_` จับคู่ชื่อคลาส
- ซอร์สเฟิร์มแวร์ ESP-IDF สำหรับ ESP32 รุ่นธรรมดา พัฒนาต่อจากไฟล์เดิม เพิ่ม UDP และคง Serial

ต้นฉบับที่ `C:\Users\may\esp32s3-wifi-csi-sensing` ไม่ถูกแก้ไขหรือลบ ชุดนี้เป็นสำเนาที่แก้ไขแยกต่างหาก ไม่ใช่การสำรองโปรเจกต์เดิมครบทุกไฟล์ โมเดลและข้อมูลฝึกยังอยู่ในต้นฉบับ

## สถานะที่ตรวจสอบแล้ว / ยังไม่ผ่าน

**ผ่าน:** 5 automated tests ครอบคลุม parser, calibration, motion, stale data, reset timestamp, sparse calibration และ integration HTTP/UDP/CSV ในเครื่องเดียวกัน; endpoint ของหน้า live ตอบ HTTP ได้

**ยังไม่ยืนยัน:** ภาพหน้าจอในเบราว์เซอร์จริง, CSI จากบอร์ดจริง, ความแม่นยำตรวจคนหรือกิจกรรม, การส่ง UDP จากบอร์ดจริง

COM3 มีอุปกรณ์ CP210x แต่เปิดพอร์ตไม่ได้ (`Access is denied`) แม้ผู้ใช้ปิดหน้าจอเดิมแล้ว จึงยังไม่ทราบว่าติดสิทธิ์ของสภาพแวดล้อมหรือโปรแกรมอื่นครอบครองพอร์ต

การ build ผ่านเครื่องมือผู้ช่วยล้มเหลวระหว่างตรวจ compiler ก่อนคอมไพล์ซอร์ส: `CreateProcess / Illegal System DLL Relocation` และ Git/MSYS permission errors ชุดนี้จึง **ไม่มี firmware binary ที่ยืนยันว่า build ผ่าน และยังไม่ได้แฟลชบอร์ด** ให้ทดสอบ build ผ่าน ESP-IDF บนเครื่องตามหัวข้อด้านล่าง

## ขอบเขตที่เหมาะกับเวลาวันครึ่ง

ส่งมอบต้นแบบ **Wi-Fi CSI Motion Monitoring with Local Dashboard**: ให้เห็นว่าข้อมูล CSI จริงเปลี่ยนเมื่อคนเคลื่อนที่ มีการคาลิเบรตและบันทึกผล พร้อมสาธิตการแจ้งสถานะเมื่ออุปกรณ์หลุด

วงเรดาร์เป็นการแสดงระดับการเปลี่ยนแปลงสัญญาณ ไม่ใช่ตำแหน่งคน ไม่ได้วัดระยะหรือมุม และไม่อ้างว่าแยกคนจากพัดลม ประตู หรือสิ่งเคลื่อนไหวอื่นได้ การ QUIET ไม่ได้หมายความว่าห้องว่าง คนที่อยู่นิ่งอาจไม่ถูกตรวจพบ

ไม่ควรอ้างการตรวจจับการล้ม การหายใจ ชีพจร โครงกระดูก หรือพิกัด 2D/3D จากชุดนี้ โมเดลเดิมมี EMPTY/WALK/STAND/SIT/WAVE ไม่มีคลาส FALL จึงยังไม่ใช่ระบบตรวจจับการล้ม

## เริ่มใช้กับเฟิร์มแวร์เดิมก่อน — ทางที่เร็วที่สุด

1. เปิด hotspot/router ที่ ESP32 เคยเชื่อมต่อและเสียบ ESP32
2. ปิด Serial Monitor, `idf.py monitor`, โปรแกรมเก็บข้อมูล และ dashboard เดิม ทุกโปรแกรมต้องปล่อย COM3
3. ดับเบิลคลิก `run-live.cmd` ในโฟลเดอร์นี้ แล้วเปิด http://127.0.0.1:8765
4. หาก Python แจ้งไม่มี serial ให้รัน `python -m pip install -r requirements.txt` ในโฟลเดอร์นี้
5. หาก COM เปลี่ยน ให้รัน `python server.py --mode serial --port COMเลขใหม่`
6. ต้องเห็น Frames เพิ่มก่อน จึงกดคาลิเบรตห้องนิ่ง 10 วินาที
7. เดินผ่านแนวระหว่าง AP กับ ESP32 แล้วสังเกตกราฟและสถานะ จากนั้นดาวน์โหลด CSV

หน้าเว็บใช้ HTTP polling ทุก 200 ms การวาดหน้าจอไม่รอ Serial และไม่ใช้ CDN หรืออินเทอร์เน็ตเพื่อโหลดกราฟ

ถ้ายัง Access is denied ให้ลองถอดเสียบ USB หลังปิดโปรแกรมที่ใช้พอร์ต แล้วดู COM ใหม่ใน Device Manager ถ้ารันเองนอกสภาพแวดล้อมผู้ช่วยเปิดได้ แสดงว่าเป็นข้อจำกัดการเข้าถึงของเครื่องมือ อย่าแฟลชซ้ำเพื่อแก้ปัญหาพอร์ตโดยไม่มีเหตุผล

### โหมดจำลอง

เปิด `run-demo.cmd` โดยหยุด server ตัวเดิมก่อน เพราะใช้พอร์ตเดียวกัน หรือ `python server.py --mode demo --http-port 8766`

ขึ้นคำว่า SIMULATION ชัดเจน ใช้ทดสอบหน้าจอเท่านั้น ไม่ใช่หลักฐานว่าบอร์ดตรวจคนได้

## Wi-Fi จริง — ขั้นที่สองหลัง Serial ผ่าน

สถาปัตยกรรมที่เลือกเพื่อลดงานในวันครึ่ง:

`AP → CSI บน ESP32 → UDP บน LAN → Python → HTTP local dashboard`

จงใจใช้ UDP ระหว่างบอร์ดกับ Python แทนเพิ่มไลบรารี WebSocket ใน firmware; หน้าเว็บใช้ HTTP polling แทน WebSocket เช่นกัน นี่เป็นการปรับขอบเขตจากระบบอ้างอิง ไม่ใช่การทำ repository อ้างอิงครบทุกฟีเจอร์

1. คอมพิวเตอร์และ ESP32 ต้องอยู่เครือข่ายเดียวกันและสื่อสารกันได้ Hotspot บางแบบแยก client ออกจากกัน ถ้า UDP ไม่ถึงแต่ Serial มา ให้ทดสอบ router/AP อื่น
2. เปิด `firmware\build-local.cmd menuconfig` ในเครื่อง เลือก **CSI Radar** แล้วตั้ง SSID, password, IPv4 ของคอมพิวเตอร์ และ UDP port 9000 โดยดู IP ของอะแดปเตอร์ที่เชื่อม AP จริง ไม่ใช่ IP ของ ESP32
3. ตรวจ target เป็น esp32 ตาม sdkconfig ที่ให้ไว้ แล้วเปิด `firmware\build-local.cmd` เพื่อ build
4. ต้อง build ผ่านก่อนแฟลช เก็บโปรเจกต์เดิมและ firmware เดิมไว้สำหรับย้อนกลับ เมื่อพร้อมรัน `firmware\build-local.cmd -p COM3 flash`
5. ปิด server Serial แล้วเปิด `run-wifi.cmd` และหน้าเว็บเดิม
6. ถ้า Windows ถามสิทธิ์เครือข่าย ให้ผู้ใช้พิจารณาอนุญาต Python บน private network ที่ใช้งาน ไม่ต้องปิด firewall ทั้งระบบ
7. ทำ calibration ใหม่ และตรวจ Frames/RSSI/CSV จากบอร์ดจริง

`build-local.cmd` ใช้ ESP-IDF v5.5.6 และตำแหน่งเครื่องมือตามที่ตรวจพบในเครื่องนี้ ใช้ build-local แยกจาก build ที่ล้มเหลวในสภาพแวดล้อมผู้ช่วย หากย้ายเครื่องต้องแก้เส้นทางเครื่องมือ

เฟิร์มแวร์ใหม่ยังส่ง Serial ควบคู่ไว้สำหรับตรวจสอบ โดยจำกัด output ไม่เกินประมาณ 20 Hz; อัตราจริงอาจต่ำกว่าเพราะขึ้นกับแพ็กเก็ตที่ได้รับ ใช้ AP BSSID เดียวเพื่อไม่รวมสัญญาณจากคนละแหล่ง และตัด CSI สองคู่แรกที่อาจมีข้อมูลไม่ถูกต้องโดยใช้ศูนย์อย่างสม่ำเสมอ จึงต้องคาลิเบรตใหม่และควรฝึกโมเดลใหม่ก่อนอ้างความแม่นยำบน firmware นี้

หากเฟรมต่ำมาก ให้สร้าง traffic ที่ AP ส่งกลับหา ESP32 เช่น ping IP ปัจจุบันของ ESP32 จากคอมพิวเตอร์ (เมื่อเครือข่ายอนุญาต) การส่ง UDP จาก ESP32 ออกไปอย่างเดียวไม่รับประกันว่าจะมี CSI ขาเข้าที่เพียงพอ ต้องวัดจำนวนเฟรมจริง

UDP receiver รุ่นนี้เลือก IP แรกที่ส่งเฟรมถูกต้อง และรับหนึ่งโหนดต่อการรัน หยุดแล้วรันใหม่ถ้า IP บอร์ดเปลี่ยน ไม่ใช่ระบบรวมหลายโหนด ไม่มีการยืนยันตัวตน จึงใช้เฉพาะเครือข่ายทดลองที่ควบคุมได้

## โมเดลกิจกรรมเดิม

เปิดด้วยคำสั่งนี้เฉพาะโมเดลท้องถิ่นที่เชื่อถือได้:

```powershell
python server.py --mode serial --port COM3 --model "C:\Users\may\esp32s3-wifi-csi-sensing\ml\models\activity_model.pkl"
```

ใช้ amplitudes ในหน่วยเดิม ×100 และ feature extraction เดิม 30 เฟรม → 260 features ไม่มีการเอา energy เพียงค่าเดียวไปแทน input เดิม หาก scikit-learn คนละเวอร์ชันกับตอนฝึก ระบบนี้ปิดโมเดลและแสดงข้อผิดพลาดแทนการซ่อน warning การ predict ได้ไม่ใช่หลักฐานว่าความแม่นยำถูกต้อง ต้องใช้ environment ตอนฝึกหรือ retrain และทดสอบกับ session ที่ไม่ใช้ฝึก

## ตารางทดสอบก่อนส่ง

1. ห้องนิ่ง 60 วินาที × 5 รอบ: นับการแจ้ง MOTION ผิดและวัดอัตราเฟรม
2. เดินผ่านพื้นที่ 60 วินาที × 5 รอบ: บันทึกเวลาที่เริ่มเดินและเวลาขึ้น MOTION เพื่อวัด latency
3. นั่ง/ยืนนิ่ง: รายงานว่า motion-only ไม่สามารถยืนยันว่ามีหรือไม่มีคน
4. ถอด USB หรือหยุดส่ง UDP: ต้องแสดง DISCONNECTED ภายในประมาณ 2–3 วินาที
5. ต่อใหม่: ข้อมูลต้องกลับมาโดยไม่ค้าง ต้องคาลิเบรตใหม่หากย้ายตำแหน่ง
6. ทดสอบพัดลม/ประตูแยกจากคน และระบุ false positive ตามจริง
7. แสดงค่าที่วัดจาก test จริงเท่านั้น ตอนนี้ยังไม่มีตัวเลข accuracy หรือ latency ของฮาร์ดแวร์
